# Geniza Knowledge Map — PGP Prototype

## Status: milestone 1 complete

Search → document node → click-to-expand relationships (places,
publications, shares-fragment documents) → visible exploration trail →
"why am I seeing this?" evidence for every edge. Working now — see
"Run it" below.

**This is a separate project from `../geniza-semantic-retrieval/`** (the
planned Friedberg Genizah Project bibliography experiment, still blocked
on data as of this writing). This project uses the **public Princeton
Geniza Project (PGP)** metadata export as a prototyping corpus. The two
datasets are never mixed, and this prototype is not a substitute for the
FGP experiment — it exists to explore a different, complementary
question (see below).

## 0. What this explores

**What becomes visible when Geniza materials are represented as a
network of relationships rather than as a collection of individual
records?** And secondarily: can an interactive representation help
researchers notice relationships that are hard to perceive through
conventional search/record interfaces?

This is an exploratory prototype, not a production scholarly database,
not a replacement for PGP or FGP, and not a Goitein-shadow detector (see
§28 non-goals below).

## 1-2. Design principle

We did not start by deciding what the "correct" Genizah ontology is. We
inspected the actual PGP export first (`results/pgp_data_profile.md`),
found that it justifies exactly three relationship types at the document
level, and built only those. Notably: the export supports
document↔place relationships but **not** document↔person relationships
(no join key), which contradicted our own prior assumption going in —
see `data_dictionary.md` for the full reasoning.

## 3. Data source and inspection

Source: [princetongenizalab/pgp-metadata](https://github.com/princetongenizalab/pgp-metadata)
(CC-BY-NC-4.0) — the Princeton Geniza Project's own published tabular
export (documents, fragments, sources, footnotes, people, places).

`results/pgp_data_profile.md` (generated by `src/inspect_pgp.py` against
the real CSVs, not the project website) documents, among other things:
- exactly where the CSVs' actual columns diverge from the dataset's own
  README (several do)
- that `documents.csv` embeds 9,557 document→place mentions across six
  role-typed columns — directly contradicting the pgp-metadata README's
  claim that place↔document links aren't in this export
- that `people.csv`/`places.csv` have **no id column at all**, only a
  name and a URL slug, and that people.csv in particular has no way to
  join back to specific documents in this export

## 4. Provenance

Every node keeps its PGP identifier and a link to the live PGP record.
`data_dictionary.md` maps every field shown in the app back to its exact
source column. No internal identifier is invented that can't be traced
to a source row.

## 5. Corpus subset

1,500 documents (of 36,239 total) by default, chosen reproducibly (fixed
random seed). Three sampling modes are supported via `config.yaml:
sample.mode`:
- `random` (default) — uniform random sample, seed 42
- `by_type` — sampled evenly across `documents.csv`'s 9 document types,
  for topical diversity
- `manual_ids` — reads `data/manual_ids.csv`, one PGPID per line, for
  investigating specific scholarly cases

## 6. Graph model

Only relationships justified by the source data (see
`results/pgp_data_profile.md` §"Relationships usable for the graph
model"):

| edge type | built from | in milestone 1? |
|---|---|---|
| Document —associated_with→ Place | `documents.csv` role columns | yes |
| Document —cited_by→ Publication | `footnotes.csv` joined to `sources.csv` | yes |
| Document —shares_fragment→ Document | `fragments.csv` (multi-pgpid rows) | yes |
| Document —associated_with→ Person | n/a — no join key in this export | **no** |
| Document —same_as/variant_of→ Document | n/a — needs the full PGPv4 DB | **no** |

No relationship is inferred from shared words or from research-assistant
tags. See `results/graph_statistics.md` (generated per run) for the
actual node/edge counts on the current sample.

## 7-13. Views, interaction, and the "why is this here" requirement

Milestone 1 implements **View 1 (Fragment/Document view)** only — search,
a single document node, user-triggered expansion, a visible exploration
trail, and an evidence popover on every edge ("why am I seeing this?").
Views 2 (Scholarly Landscape / embeddings) and 3 (Temporal Landscape) are
explicitly deferred — see §23-25 below and `src/embeddings.py`,
`src/similarity.py`.

Every edge in the graph carries an `evidence` string built from the raw
source row(s) that justify it — never a generated claim. Clicking an edge
in the app shows exactly that string.

## 14. The eventual research experiment

Not implemented yet, and shouldn't be — this milestone exists to make
that future comparison (record/search browsing vs. this relational map)
possible, not to run it.

## 15-16. Discovery logging and "flag as interesting"

Both implemented client-side, entirely local (`localStorage`/
`sessionStorage`, no personal information, no server): every select/
expand/navigate action is logged with the schema from spec §15; a "Flag
as interesting" button on every node records the starting node, current
node, full exploration path, and timestamp. Both are exportable as JSON
from the sidebar ("Export session log" / "Export flagged discoveries").

## 17-19. Interface

Desktop-first, matching the proposed layout: a left sidebar (current
path above, node details below), the graph visualization dominating the
right side. No cards-as-decoration, no gradients, no gamification, no
giant dashboard of metrics. Search is the entry point, not the
destination — selecting a search result drops you into a single document
node, not a results list to read and close.

## 20-21. Technology and pipeline

```text
Python (pandas) → normalized JSON → static web app (vanilla JS + Cytoscape.js)
```

No backend, no database — the sample is small enough (≤5,000 documents)
that a static JSON bundle fetched by the browser is simplest and fully
reproducible. Cytoscape.js is vendored locally in
`webapp/js/vendor/cytoscape.min.js` (not loaded from a CDN), so the app
works fully offline once the data is built.

```text
src/
    inspect_pgp.py   # Stage 0 — real schema/data inspection, read-only
    normalize.py     # Stage 1 — reproducible document subset + field cleaning
    build_graph.py   # Stage 2 — nodes/edges from justified relationships only
    export.py         # Stage 3 — copy processed JSON into webapp/data/
    embeddings.py    # Stage 4 (milestone 2, NOT implemented)
    similarity.py    # Stage 4 (milestone 2, NOT implemented)
```

`data/raw/` is fetched, never committed (66MB, third-party, CC-BY-NC) and
never modified by the pipeline. `data/processed/` and `webapp/data/` are
generated outputs — small enough to commit so the app runs without
re-fetching anything.

## Run it

```bash
pip install -r requirements.txt

# Fetch the raw PGP metadata export (public, CC-BY-NC-4.0):
git clone --depth 1 https://github.com/princetongenizalab/pgp-metadata data/raw/pgp-metadata

# Build the graph:
python run_pipeline.py

# Serve the static app (no build step):
cd webapp && python3 -m http.server 8000
# then open http://localhost:8000/
```

The committed `data/processed/` and `webapp/data/` JSON already reflect a
1,500-document random sample (seed 42), so `cd webapp && python3 -m
http.server 8000` alone is enough to try the app without fetching
anything first.

## 23-25. Milestones

- **Milestone 1 (done):** search, document node, expand relationships,
  exploration path, provenance/evidence for every edge.
- **Milestone 2 (not started):** semantic-neighborhood layer, visually
  and label-distinguished from explicit relationships ("computationally
  similar", never "related"). Only worth attempting after milestone 1
  has actually been used and judged worth extending.
- **Milestone 3 (not started):** scholarly/temporal landscape views.

## 26. What success looks like

Not "we visualized N documents." Success is a researcher starting at one
fragment and, by following relationships, ending up somewhere they
wouldn't have thought to search for. `results/example_paths.json` has one
real (not cherry-picked — captured during ordinary smoke-testing)
instance of this: two documents with no shared vocabulary, connected only
because both mention the Mediterranean Sea.

## 27. Research questions log

See `results/research_questions.md` — a running log of observations, not
premature conclusions.

## 28. Non-goals

Not a replacement for PGP or FGP, not a general Genizah search engine,
not an automated scholarly-interpretation engine, not an authoritative
ontology, not a chatbot, not a claim to reveal "the true structure" of
the Genizah, and explicitly **not** a Goitein-shadow detector at this
stage (see spec discussion — that requires a separate, later
operationalization).

## 29. Ethical / scholarly requirements

The app distinguishes source-established relationships (solid, in this
milestone the only kind that exists), computational relationships (would
be dashed, milestone 2, none exist yet), and human interpretation (the
`human_verdict`/flagged-discovery mechanism — never auto-filled). See
`data_dictionary.md` and the "why am I seeing this?" evidence popover.
