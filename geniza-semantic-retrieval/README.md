# Genizah Semantic Retrieval — a modern extension of "In the Shadow of Goitein"

## Status: blocked on data (Stage 0 only)

This project is scaffolded but **has not run past data inspection**. No
Friedberg-style bibliographic corpus is present under `data/`, and per this
project's own research-discipline rule, the pipeline does not fabricate or
download a substitute one. Run `python run_experiment.py` to see this for
yourself: it produces `results/data_profile.md`, a precise report of what's
missing, and stops. See that file for exactly what's needed to unblock it.

Everything below describes the pilot as designed; only Stage 0
(`src/data_profile.py`) currently does real work.

## 0. Project identity

This is a small research prototype directly inspired by:

> Christopher Stokoe, Gabriele Ferrario, and Ben Outhwaite (2014),
> "In the Shadow of Goitein: Text Mining the Cairo Genizah," *Manuscript
> Cultures* 7, pp. 29–34.
> ([PDF](https://www.csmc.uni-hamburg.de/publications/mc/files/articles/mc07-stokoe-ferrario-outhwaite.pdf))

The 2014 paper proposed using computational methods — a term-weighted
vocabulary, Named Entity Recognition, and topic modelling — to mine
published editions, commentaries, and secondary literature about the Cairo
Genizah, in order to generate richer descriptive metadata than the raw
manuscript collection carries on its own, and so enable better discovery.

This project is a small modern extension of that research direction, not
an unrelated machine-learning experiment.

## 1. Research question

**Can modern semantic representations recover relationships among Genizah
publications that lexical representations fail to capture?**

More specifically: if the same bibliographic corpus is represented first
through lexical similarity and then through semantic embeddings, do the two
representations produce different scholarly neighborhoods?

The pilot investigates whether semantic representations can reveal:

- related concepts expressed with different terminology
- relationships across Hebrew/English terminology
- related publications that share few surface words
- relationships between documents described from different scholarly
  perspectives
- potentially neglected connections in the scholarly literature

We do **not** assume beforehand that semantic retrieval is superior. The
purpose of the pilot is to determine whether there is a signal worth
investigating.

## 3. Important distinction

This pilot is **not** a reproduction of the entire 2014 experiment. It does
not attempt the complete text-mining pipeline, the full NER work, the
original topic-model analysis, the complete Cambridge corpus, or the
original evaluation procedures.

It is, precisely: *"a focused computational extension inspired by the
retrieval and discovery problem formulated by Stokoe, Ferrario & Outhwaite
(2014)."*

See `results/data_profile.md` (regenerated by `src/data_profile.py` on

## 5. Corpus design

The pilot targets **100–500 bibliographic records** — a topically diverse
subset, not the full ~200,000-reference Friedberg Genizah Project database
— chosen for methodological debugging and discovery, not exhaustive
coverage.

## 6. What counts as a document

Two canonical textual representations, switchable via `config.yaml:
representation.mode`:

- **Representation A — title only**: `title`
- **Representation B — bibliographic text**: `title`, `authors`, `venue`,
  `year`, `keywords`, `abstract`, `notes` — using only fields that actually
  exist in the loaded corpus, and never a pre-assigned subject/topic
  category (that would leak the answer the pilot is trying to discover
  independently).

## 7. Lexical baseline

TF-IDF + cosine similarity (primary), BM25 (optional second baseline).
Preprocessing is conservative by design: no aggressive stemming,
translation, or rewriting unless explicitly configured, and any such
preprocessing is applied and reported per language separately for
multilingual records.

## 8. Semantic representation

Embeddings over the same canonical text, using a multilingual model capable
of representing Hebrew and English (model name, version, dimensionality,
and normalization procedure are all recorded in `config.yaml` and echoed
into `results/report.md` once the pipeline runs). Cosine similarity, same
candidate corpus as the lexical baseline.

## 9-10. Experimental design

**Phase 1 (discovery):** ~30–50 seed publications selected with a
reproducible random seed; for each, top-10 lexical and top-10 semantic
neighbors are retrieved and stored, unbiased by hand-picking.

**Phase 2 (scholarly inspection):** ~3–10 candidate-interesting cases are
identified from Phase 1 — where semantic retrieval appears to expose a
relationship (terminology mismatch, conceptual relationship expressed
differently, multilingual relationship, fragment-centered relationship, or
a lexical false positive on generic Genizah vocabulary) that lexical
retrieval does not. These are hypotheses for human inspection, not
automatic conclusions.

## 11. Retrieval vs. interpretation

The system never asserts "this is a meaningful scholarly connection." It
produces `candidate_interesting_case = TRUE` with supporting evidence
(ranks, overlap, shared entities/identifiers, dates, languages, titles,
abstracts, similarity scores) and leaves `human_verdict` blank for a person
to fill in (`relevant`, `partially relevant`, `not relevant`, `surprising
connection`, `lexical false positive`, `semantic false positive`,
`duplicate/near duplicate`, `unclear`).

## 12-14. Outputs

- `results/data_profile.md` — corpus inspection / data-requirement report
- `results/retrieval_comparison.csv` — full seed × method × rank table
- `results/interesting_cases.csv` — Phase 2 candidates with evidence
- `results/corpus_statistics.csv` — descriptive corpus stats
- `results/corpus_map.html` — interactive 2D semantic map
- `results/report.md` — the full write-up (see structure below)

No accuracy metric is invented in the absence of ground truth. Reported
measures are descriptive: top-10 overlap, Jaccard similarity between
retrieval sets, lexical overlap of semantic-only results, publication-year
and language distributions, duplicate rate.

## 15-18. Optional clustering + visualizations

UMAP/PCA over the embedding space only after retrieval itself is validated;
any resulting groups are labeled "embedding-space neighborhoods," never
"true topics." Three visualizations: the corpus map; a side-by-side
lexical-vs-semantic panel per interesting seed; and a focused
semantic-only-discoveries table, where any generated explanation is
explicitly labeled `machine_generated_hypothesis` and kept separate from
`human_verdict`.

## 19. Report structure (`results/report.md`)

1. Background (the 2014 paper's argument; the "Goitein shadow")
2. Research question
3. Relation to the 2014 work (what stays the same / what changes)
4. Corpus
5. Methods
6. Retrieval results
7. Candidate discoveries
8. Human assessment (left for manual scholarly evaluation)
9. Limitations
10. Next study

## 20. On the "Goitein shadow"

This pilot does **not** claim to have detected the Goitein shadow — that
requires a separate operationalization. It establishes only the more basic
question: can modern semantic retrieval reveal scholarly relationships that
are difficult to recover through lexical retrieval? A convincing answer
would motivate a follow-up study asking whether semantic retrieval can
expose parts of the Genizah bibliography structurally less connected to the
dominant scholarly vocabulary associated with Goitein.

## 23. Research discipline

The pilot does not optimize for a positive result. If semantic retrieval
turns out to produce mostly noise, that gets reported. If lexical retrieval
performs surprisingly well, that gets reported. If both methods retrieve
essentially the same papers, that gets reported. The goal is to discover
whether there is a research phenomenon worth pursuing — not to manufacture
one. This is also why the pipeline currently stops rather than running
against invented data: a demo built on fabricated records would not be
evidence of anything.
